## AI Coding Flow 全局规则

### 分通道（仅限已接入的仓库）

- 本节规则只在仓库根目录有 `.ai/` 目录时生效。其他仓库照常工作，不要主动引入本流程。
- 任何开发任务，先数步数、判断通道，再动手。步数 ≤ 2、只改一个文件、验收标准一句话说得清，这三条**同时**满足才走 Vibe 通道；其余一律走 Spec 产线（`/flow`）。拿不准时走 Spec 产线，并说明是哪一条没满足。用户明确指定了通道时，按用户说的办。

### 有据可依（grounding）

- 断言某个 API、字段、配置、依赖存在之前，先读源码确认，不能凭训练记忆或项目名字猜测。
- 每条关键论断标出处：`file:line`。找不到出处的东西，在产物里明确标「新增」，不要和已有代码混在一起说。
- 召回到的历史资料（spec、相似变更）只信标注了来源的部分；无法定位来源的，视为不存在。
- 仓库有 `.ai/kb/` 时，找代码先读 `.ai/kb/index.md` 或执行 `"$HOME/.ai-flow/bin/flowctl" kb recall`，只读命中的页，再 grep 补漏；页里的 `file:line` 仍要打开核对，知识库本身不是证据。

### 不擅自扩大范围

- 只做任务或验收标准里写明的改动；顺手发现的问题记下来，不在本次改动里顺手修。
- 除非用户要求，不新增任务描述之外的文件、依赖或配置项。

### 完成前必须验证

- 声明"完成"之前，实际跑一次相关测试或构建命令，把命令和真实输出（或至少结论）报给用户。
- 命令执行失败、报错、或输出不确定时，如实说明失败，不能宣称成功。
- 没有可跑的验证手段时，明确说明"未验证"，不要用推测代替验证结果。

### 拿不准就停下问

- 需求、验收标准、边界条件有歧义时，停下来问用户，不要自己编一个假设往下走。
- 唯一例外：用户已经明确表示"你自己判断就行"。

### Git 安全

- 未经用户明确确认，不执行破坏性 git 操作：`push --force`、`reset --hard`、`clean -f`、删除分支、覆盖式提交历史。
- 提交前如实说明本次改动范围，不要把无关文件一起提交。

### 流程状态

- 流程状态都保存在仓库的 `.ai/` 目录里，不在对话上下文里。
- 换会话、换工具、中途继续，先运行 `"$HOME/.ai-flow/bin/flowctl" status`，查看当前变更和下一步，再决定怎么做，不要凭对话记忆猜进度。
