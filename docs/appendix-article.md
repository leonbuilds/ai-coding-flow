# 附录 · 原文要点速记

来源：货拉拉技术《个人提效，攒不成组织提效：货拉拉 AI Coding 落地实践》，2026-09-16。本节只做概括，不大段引用原文；引用均控制在一句以内并标明是引用。

## 原文的核心判断

标题本身就是原文的核心论点：个人层面的 AI 提效（会用工具、单点效率变高）不会自动累加成组织层面的提效。原因是效率提升散落在个人手里，没有沉淀、没有共享、没有可比较的度量，团队整体的产出质量和速度并不会因为个别人用得好而系统性变好。

## 三阶段落地

原文把团队从"能用 AI"到"AI 深度参与研发全流程"分成三个递进阶段：

1. **普及**：把下限抬起来——解决"会用工具，但不知道手上这个活该怎么让 AI 干"的问题。做法是统一的编码约束加照着就能跑的高频场景手册。
2. **规范驱动**：让 AI 按规范写——解决"能用了，但不稳定，方案质量看个人状态"的问题。做法是引入结构化的规范（spec）和产线化的流程，把"怎么做"从个人经验变成可复用的文档。
3. **AI Native**：全生命周期闭环——解决"做过的需求没有沉淀，踩过的坑还会再踩"的问题。做法是把复盘、审查发现、线上问题都回写成资产，下一次自动生效。

## 统一工作台 AiBox

原文提出一个组织级的统一工作台，集中管理四类配置（Rules、Skills、Commands、MCP），由平台统一维护并下发到每个人的 IDE，同时承担治理职能（准入、用量统计、合规、审计）和流程入口的角色。

## 三个坑

原文总结了几个容易踩的坑，其中和本方案关系最直接的两个：

- **上下文管理**：主 Agent 的上下文被无关信息占满，会拖累后续推理质量；需要用侦察角色（scout 一类）保持主上下文干净，只把有理由的候选交给人筛选。
- **主从双 Agent（独立审查）**：AI 生成的代码看起来通顺但可能引用了不存在的 API 或字段，需要第二只眼睛来核对，并且这只眼睛的上下文必须独立，否则会跟着第一个 Agent 一起产生幻觉。

## 个人版的取舍对照表

| 维度 | 原文（组织级 AiBox） | 本方案（个人版） |
|---|---|---|
| 服务对象 | 团队/组织全员 | 使用者本人 |
| 配置分发 | 平台统一维护，下发到每个人的 IDE | 一个仓库作为唯一真相源，`wb sync` 装到自己的 Claude Code 和 Codex 两端（见 [08-workbench.md](08-workbench.md)） |
| 治理 | 工具准入审计、用量统计、合规检查 | 简化为 `wb doctor` 的漂移检测 + 变更档案的过程留痕，不做多人审计 |
| 流程驱动 | 规范驱动 + 全流程平台化 | 六步 spec 产线 + 分通道硬标准，靠本地 CLI（`flowctl`）而非平台（见 [01-lanes.md](01-lanes.md)、[02-pipeline.md](02-pipeline.md)） |
| 审查独立性 | "主从双 Agent"作为通用原则提出 | 细化成三级独立性（L1 上下文/L2 模型/L3 厂商），且模型/引擎由用户每次现场选择而非平台指派（见 [07-models-and-hosts.md](07-models-and-hosts.md)） |
| 度量 | 组织级效能对比（原文未展开具体公式） | 具体到可复算的 FPY、AI 代码占比、采纳率、spec 命中率/误导率、存活率公式，并写明每个指标的盲区（见 [04-metrics.md](04-metrics.md)） |
| 知识沉淀 | 平台统一的规范库，团队共享 | 仓库级 + 全局两层 spec 库，个人复盘/线上反哺回写，跨仓库通用的部分放 `~/.ai-flow/specs`（见 [03-spec-library.md](03-spec-library.md)、[05-closed-loop.md](05-closed-loop.md)） |
| 多厂商支持 | 未强调 | Claude Code / Codex 双端通用，四种"谁写谁审"组合都有明确的执行路径（见 [07-models-and-hosts.md](07-models-and-hosts.md)） |
| 团队管理、异步云端 Agent | 原文的一部分（治理、平台化能力） | 明确排除在范围之外（见 [09-roadmap.md](09-roadmap.md)） |
