# 01 · 分通道

## 硬标准

任何开发任务，先数步数、判断通道，再动手。走 **Vibe 通道**需要**同时**满足下面三条：

1. **步数 ≤ 2**（阈值可配置，见下）。一步指一处独立的改动，加上对它的验证。
2. **只改一个文件**。
3. **验收标准一句话说得清**，没有需要澄清的地方。

其余情况一律走 **Spec 产线**（[02-pipeline.md](02-pipeline.md)）。拿不准时也走产线，并说明是哪一条没满足。用户明确指定了通道时，按用户说的办。

阈值来自 `.ai/config.json` 的 `lane_step_threshold`（默认 `2`），由 `flowctl init` 写入仓库时生成的默认配置。

来源：`skills/flow/SKILL.md`、`rules/global.md`。`rules/global.md` 里这条规则只在仓库根目录存在 `.ai/` 时生效——没接入本流程的仓库不受影响。

## 通道决定什么，不决定什么

- Vibe 通道：不建变更（不跑 `flowctl new`），不召回 spec，直接改，跑一次相关测试或编译就结束。有对应场景手册（playbook）时照着做。
- Spec 产线：进入六步产线，从 `/flow-propose` 开始，全程留痕、可回溯。
- 读代码分析、代码评审（CR）本身不产出代码改动，不占用通道判断，但产出可以作为后续 Spec 产线的输入。

## 五个例子

| # | 任务 | 判到哪条通道 | 为什么 |
|---|---|---|---|
| 1 | 把某个接口的超时时间从 3s 改成 5s，只涉及一个 config 文件 | **Vibe** | 步数 1（改一处配置值）、单文件、验收一句话说清（"这个接口超时改成 5s"），三条全满足 |
| 2 | 给订单模块加 `remark` 字段，并加一个按 `remark` 模糊查询的接口 | **Spec 产线** | 至少涉及数据模型、迁移文件、service 层、接口层、测试共 4+ 个文件，"只改一个文件"不满足；对应场景手册 [add-field-api.md](../playbooks/add-field-api.md) |
| 3 | 给 `TransitionStatus` 方法补单元测试，不改被测代码，一次写完 | **Vibe** | 只新增/修改一个测试文件，步数 1，验收命令明确（跑这个测试文件）；对应场景手册 [unit-test.md](../playbooks/unit-test.md)。如果补测试过程中发现被测代码本身要改，则转 Spec 产线 |
| 4 | 订单导出接口在结果集为空时返回 500，需要修复并补回归测试 | **Spec 产线** | 排查后确认修复涉及 `export.go` 和它的回归测试文件，共 2 个文件，"只改一个文件"不满足，尽管步数、验收标准都清晰；对应场景手册 [bugfix.md](../playbooks/bugfix.md)。若排查后确认修复真的只落在一个文件里，才会退回 Vibe |
| 5 | "优化一下订单模块的性能" | **Spec 产线**（拿不准） | 验收标准说不清（"优化"到什么程度算完成？没有一句话能界定），且步数、涉及文件数都无法提前判断；按规则拿不准时走产线，并向用户说明是"验收标准"这一条没满足 |

## Playbooks 列表

Vibe 通道和日常小活照着场景手册做。所有 playbook 都包含：走哪个通道的判断、准备事项、提示词模板、期望产出、验收清单、常见翻车点、一个完整示例。

| Playbook | 适用场景 | 默认通道倾向 |
|---|---|---|
| [read-code.md](../playbooks/read-code.md) | 接手不熟悉的代码，动手改之前先搞清楚怎么运作 | 不产出代码改动，不占通道判断；结论可作为 `/flow-propose` 的输入 |
| [add-field-api.md](../playbooks/add-field-api.md) | 给已有模块加字段（含迁移）+ 配套查询接口 | 几乎总是 Spec 产线（涉及 model/迁移/service/接口多个文件） |
| [bugfix.md](../playbooks/bugfix.md) | 复现、定位、修复一个具体 bug | 看修复本身范围，不看排查过程长短；从线上报警/测试报告发现的先走 `/flow-incident` |
| [unit-test.md](../playbooks/unit-test.md) | 给已有方法补单元测试，不改被测代码 | 多数情况 Vibe；发现要改被测代码或测试场景有争议时转 Spec 产线 |
| [code-review.md](../playbooks/code-review.md) | 对当前分支改动做结构化评审 | 不占通道判断；Spec 产线内置的审查用 `/flow-review`，本手册用于产线之外的日常 CR |
