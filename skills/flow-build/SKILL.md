# flow-build · 逐任务实现

## 每个任务一轮循环

从 tasks.md 里取第一个未勾选的任务 `T<n>`，然后：

1. **开工前打快照**：`"$HOME/.ai-flow/bin/flowctl" snapshot T<n> base`
   打之前工作区里应该只有已经完成的任务。如果有无关的改动，先请用户处理掉。
2. **只读这个任务的输入**：包括它列出的文件、design 里对应的 Delta、相关的 spec。不要重读整个变更。
3. **一次写完首版**：严格按 design 实现，不要超出任务范围。用到的每个 API 和字段，都要先在源码里确认存在。
4. **立刻打 v1 快照**：`"$HOME/.ai-flow/bin/flowctl" snapshot T<n> v1`
   写完首版就打，在跑测试、自我修正、人工修改**之前**。FPY 衡量的是首版质量，打晚了这个指标就失真了。
5. **跑验收**：执行任务里写的验收命令。失败就修，修改都会计入 FPY 的「被改行」。
6. **人工过目**：简要说明改了什么，以及验收结果。用户可以自己改代码，也可以提意见让你改。
7. **验收通过并且用户认可后**：`"$HOME/.ai-flow/bin/flowctl" snapshot T<n> final`，然后在 tasks.md 里把这一项勾成 `- [x]`。
8. **建议每个任务单独提交一次**（用户同意后再提交），方便单独回退。

## 失败与回退

- 同一个任务修了 3 轮验收还过不了，就停下来，请用户判断：是任务拆得不对，还是方案本身有问题。
- 回退只回退这一个任务，而且只恢复这个任务改过的文件：
  `git restore --source=refs/flow/<变更>/T<n>/base -- <这个任务改过的文件>`
  这个命令会覆盖文件，执行前先把要回退的文件列表给用户确认。
  这个任务**新建**的文件在 base 里不存在，`git restore` 会报 pathspec 错误。这类文件改为直接删除（同样先给用户确认）。
  用 `git diff --name-status refs/flow/<变更>/T<n>/base` 可以区分哪些是修改的文件（M），哪些是新建的文件（A）。
- **方案本身错了**（接口对不上、漏了约束）：不要在代码里绕过去。停下来改 design.md，回到 `/flow-design` 的人工门禁；受影响的任务重新拆。
