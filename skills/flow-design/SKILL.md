# flow-design · 技术方案

## 输入（只读这些）

- `proposal.md`：业务意图、边界、AC，以及上下文清单里**勾选了的**条目；
- 勾选的 spec 全文、勾选的知识库页、勾选的代码入口，以及沿着调用链实际需要读到的代码。

## 步骤

1. **先读源码，再写方案**。方案里提到的每个类、方法、字段、表、配置项、依赖，都要写上 `file:line`。在源码里找不到的，一律标「新增」，不能假设它已经存在。
2. **圈影响面**：仓库有 `.ai/kb/` 时，用 `.ai/kb/architecture/module-dependencies.md` 的依赖图、涉及模块页的「上下游」和对应业务域的 SDD 列出会被波及的模块、接口、表；每一条都回源码核对后写进「架构约束与风险」。知识库里没有的依赖，自己顺着 import 和调用找。
3. 按模板填写 design.md。「Delta」一节按 ADDED / MODIFIED / REMOVED 分类列出，每一条后面会拆成一个或几个任务。
4. 在「验证方式」里，为每条 AC 写出具体的验证手段：命令、测试名或操作步骤。
5. 如果勾选的 spec 和现有代码冲突，不要自己挑一个。把冲突写进「架构约束与风险」，交给用户决定。
6. `"$HOME/.ai-flow/bin/flowctl" trace design generated`
7. **人工门禁：停下来**，请用户评审。用户每提一轮修改意见，改完后重复第 6 步。

## 放行

用户确认后：删掉 `<!-- flow:todo -->`，执行 `"$HOME/.ai-flow/bin/flowctl" trace design accepted`，然后提示下一步是 `/flow-tasks`。

## 反模式

- 凭印象写接口签名。一律回源码核对。
- 方案里出现「可能」「应该有」这类措辞。要么查到确切位置，要么标成新增。
- 顺手做 proposal 没要求的重构。确实需要的话，写进风险一节，请用户决定做不做。
