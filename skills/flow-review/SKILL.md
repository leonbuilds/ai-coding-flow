# flow-review · 独立审查

AI 很擅长写出看起来很对的代码：调用了不存在的 API、虚构了字段、配错了依赖。审查必须由「第二只眼睛」来做，并且这只眼睛要**独立**：审查者如果复用实现者的上下文，就会跟着实现者一起产生幻觉。

命令入口：`"$HOME/.ai-flow/bin/flowctl"`（下文简写为 flowctl）。

## 每一轮审查

1. **选择审查者**：每一轮都要问用户。
   - 执行 `flowctl models verifier --json`；
   - 向用户提问，让用户选择引擎和模型。选项这样排：
     - 第 2 轮起，第一个选项放「和上一轮一样」；
     - 然后列出另一家厂商的模型，标注「跨厂商，独立性最高（L3）」；
     - 再列出同一家厂商的其他模型，标注 L2；
     - 最后是和你自己相同的模型，标注 L1。
   - Codex 模型要附上推理档位，让用户一起选；
   - CLI 不可用的引擎不要列出来；
   - 提醒用户：审查者的能力不应低于实现者。
2. **开审**：
   ```
   flowctl verify start --host <宿主> --host-model <你自己当前的模型> --engine <引擎> --model <模型> [--reasoning <档位>]
   ```
   它会做这几件事：把当前工作区（包括未跟踪的文件）存成审查终点；生成 prompt，内容只有 diff 范围、验收命令，以及审查者上一轮自己提的发现；启动审查者。
   - **外部引擎**（跨厂商，或者宿主是 Codex）：flowctl 会自己运行、等待结果，并记录这一轮。
   - **宿主是 Claude，且选的是 claude**：输出里 `mode` 是 `native`。这时用 Agent 工具启动 `flow-verifier` 子 Agent，`model` 传用户选的模型，prompt **原样使用** `prompt_file` 的全文，不增不减。把子 Agent 的完整回复写入 `out_file`，然后执行 `flowctl verify record`。
3. **不许夹带**：不能往审查者的 prompt 里加你的实现思路、「我已确认 X 存在」这类结论，或者代码摘要。审查者必须自己回源码去查。
4. **看结果**：flowctl 会把这一轮追加到 review.md 的轮次表里。
   - **新增文件的警告**：审查期间出现了未被忽略的新文件（多半是测试缓存）。结论仍然有效，但要确认这些文件后删除，或者加进 .gitignore。
   - **INVALID**：审查者改动了已有文件，或者输出里没有唯一的一行结论。先查清楚改了什么，并恢复，再重新开一轮。
   - **REJECT**：逐条修复。修的时候要对照源码确认，不要照着审查意见的字面去改。在 review.md 的「修复记录」里写明：修的是哪一条发现、改了哪里、怎么确认的。修完回到第 1 步。
   - **PASS**：进入下一节。
5. 连续 REJECT 3 轮后，停下来交给用户判断。

## 放行后：给 spec 打分

读 `recalled.json`，对里面每一条 spec 下一个判定，填进 review.md 的「spec 反馈」表，然后逐条执行 `flowctl score <spec-id> <判定> --note "<一句话>"`。判定有三种：

- `hit`：用上了，而且有帮助；
- `unused`：召回了但与本次无关；
- `mislead`：把实现或方案带偏了，note 里写明偏在哪里。

最后删掉 `<!-- flow:todo -->`，并提示下一步是 `/flow-retro`。
