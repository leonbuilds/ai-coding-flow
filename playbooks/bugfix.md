# Bug 修复

适用场景：线上或测试环境报了一个具体的 bug，需要复现、定位、修复。

## 走哪个通道

看修复本身的范围，不看排查过程的长短：

- 排查之后确认改动只涉及一个文件、步数 ≤ 2、验收一句话说清（比如"这个接口传 xx 参数不再报错"）：走 **Vibe 通道**，直接改。
- 修复涉及多个文件、动了接口行为或数据结构、或者根因指向设计问题：走 **Spec 产线**，用 `/flow` 或 `/flow-propose` 起个变更，把复现步骤和根因作为需求原文的一部分。
- 如果 bug 是从线上报警或测试报告发现的，先用 `/flow-incident` 记录问题、追到相关的历史变更，再决定怎么修。

## 准备

- 收集能复现问题的最小信息：请求参数、报错信息或堆栈、触发条件、影响范围。
- 如果有相关的日志或监控截图，一并提供，不要只描述"报错了"。
- 说明这个 bug 是不是最近改动引入的（如果知道大概时间范围）。

## 提示词模板

```
帮我修复一个 bug：<一句话描述现象>

复现信息：
- 触发条件/请求参数：<具体值>
- 实际结果：<报错信息、堆栈，或错误的返回值>
- 预期结果：<应该是什么样>
- 影响范围：<全部请求还是特定条件>

要求：
- 先复现问题（写一个能触发它的最小测试或脚本），确认复现之后再定位根因
- 根因要有证据（读到的具体代码 file:line），不要凭经验猜一个"可能是这里"就直接改
- 修复只改动定位到的根因位置，不要顺带重构或改动无关代码
- 修复后补一个回归测试，覆盖这次的触发条件，防止再犯
- 报告：复现方式、根因、改动了哪些文件、回归测试跑的结果
```

## 期望产出

- **复现**：一个能稳定触发问题的测试或步骤。
- **根因**：具体到 `file:line`，说明为什么会导致这个现象，不是"大概是这块逻辑有问题"。
- **最小修复**：改动范围尽量小，只解决这个根因。
- **回归测试**：覆盖本次的触发条件，跑通。
- **报告**：复现步骤、根因说明、改动清单、测试结果。

## 验收

- 按报告里的复现步骤，确认改动前确实能触发问题。
- 跑回归测试，报告实际输出，确认改动后问题消失。
- 跑一次相关的既有测试，确认没有引入新的失败。
- 检查改动范围是否只涉及根因，没有夹带无关修改。
- 如果根因指向设计层面的问题（比如某个假设在别处也存在），确认是否需要转成 spec 或另开一个变更处理，而不是在这次顺手全改了。

## 常见翻车

- **没复现就直接改**：凭猜测"应该是这里"改代码，改完问题可能没解决或者掩盖了真正原因。提示词模板要求先复现再定位。
- **根因说不出具体代码位置**：停留在"大概是并发问题"这种模糊结论。要求根因带 file:line 证据。
- **修复顺带重构了一大片**：定位到一行的问题，改了一个文件甚至一个模块。要求修复范围只覆盖根因。
- **没有回归测试，下次同样的输入又炸**：期望产出里强制要求补回归测试。
- **只在开发环境验证，没确认和线上报的条件一致**：验收时对照最初的复现信息逐项核对，而不是随便试一下就算过。

## 示例

现象：订单导出接口，当订单列表为空时返回 500 而不是空文件。

```
帮我修复一个 bug：订单导出接口在没有匹配订单时返回 500

复现信息：
- 触发条件/请求参数：GET /api/orders/export?status=cancelled，且该状态下没有订单
- 实际结果：HTTP 500，日志里是 nil pointer dereference
- 预期结果：返回一个空的导出文件（只有表头），HTTP 200
- 影响范围：只在查询结果为空集时出现

要求：
- 先复现问题（写一个能触发它的最小测试或脚本），确认复现之后再定位根因
- 根因要有证据（读到的具体代码 file:line），不要凭经验猜一个"可能是这里"就直接改
- 修复只改动定位到的根因位置，不要顺带重构或改动无关代码
- 修复后补一个回归测试，覆盖这次的触发条件，防止再犯
- 报告：复现方式、根因、改动了哪些文件、回归测试跑的结果
```

预期结果：定位到 `internal/order/export.go:45` 生成表头时假设 `orders[0]` 一定存在，空切片时越界/空指针；修复为空集时也生成表头；补一个"空结果集导出"的回归测试；报告里给出修复前后的测试输出对比。
