# 代码评审（CR）

适用场景：对当前分支的改动做一次结构化评审，在提交或合并前发现问题。

## 走哪个通道

CR 本身不改代码，不占用 Vibe/Spec 的通道判断。它是两个场景的一部分：

- **Spec 产线内置的审查**：`/flow-review` 会用 `flowctl verify` 调度独立的 `flow-verifier` 角色（引擎和模型每轮由你选择，推荐跨厂商），这是产线的硬门禁，不需要额外走这个手册。
- **Vibe 通道或产线之外的日常 CR**：比如提交前想自己先过一遍、或者评审别人的分支，直接用本手册的提示词模板。

## 准备

- 明确评审的对比基准（和哪个分支/commit 比），只看这次改动的 diff，不要评审整个仓库。
- 说明这次改动对应的需求或目的（一句话即可），评审时要对照它，不只是看代码本身好不好看。
- 如果仓库有编码约定（`CLAUDE.md`/`AGENTS.md` 或专门的规范文档），确认评审时会用到。

## 提示词模板

```
对 <分支/commit 范围> 的改动做一次结构化代码评审。

背景：
- 对比基准：<比如 "main 到当前分支" 或 "commit A 到 commit B">
- 这次改动要做什么：<一句话>
- 需要重点关注：<可选，比如"这次改了并发逻辑，重点看线程安全">

要求：
- 按严重级别分类输出：阻塞（必须改）、建议（最好改）、可选（风格类）
- 每一条问题必须附带证据：具体 file:line 和一句话说明问题在哪、为什么是问题
- 不要只提风格类意见（命名、格式化）冒充全部结论，重点看：逻辑正确性、边界条件、错误处理、是否匹配需求、是否引入了未声明的行为变化
- 对照这次改动要做的事，指出有没有超出范围的改动
- 找不到问题的地方不要硬凑，如实说"这部分没发现问题"
```

## 期望产出

一份结构化评审报告：

- **阻塞问题**：逻辑错误、明显 bug、破坏性变更、安全问题。每条带 `file:line` 和证据。
- **建议问题**：可以更好但不是必须现在改的（性能、可读性、测试覆盖不足）。
- **可选/风格**：命名、格式化类，单独放最后一段，不占主要篇幅。
- **范围核对**：这次改动是否有超出声明目的的部分。
- **总体结论**：能不能合并，还是需要先处理阻塞问题。

## 验收

- 抽查报告里几条"阻塞"问题，确认证据（file:line）指向的代码确实存在这个问题，不是误报。
- 确认报告没有把"阻塞"和"风格建议"混在一起、或者用风格意见撑数量。
- 对照这次改动的实际目的，检查报告是否指出了范围外的改动（如果有）。
- 如果结论是"可以合并"，抽查是否真的没有遗漏明显问题，而不是评审得太粗。

## 常见翻车

- **通篇都是命名和格式化建议，没碰逻辑问题**：提示词模板明确要求按严重级别分类，且重点看逻辑正确性而非风格。
- **问题没有证据，只有"这里感觉不太对"**：要求每条必须带 file:line 和具体说明。
- **评审范围扩大到整个文件，而不是这次的改动**：准备阶段明确对比基准，只看 diff。
- **没有对照需求，只是孤立地看代码好不好**：要求对照这次改动的目的判断是否匹配。
- **为了显得全面，把可能的问题都列成阻塞级**：要求区分阻塞/建议/可选，避免虚报严重度。

## 示例

背景：给订单模块加了 remark 字段和查询接口，提交前自己先 CR 一遍。

```
对 main 到当前分支的改动做一次结构化代码评审。

背景：
- 对比基准：main 到当前分支
- 这次改动要做什么：给订单加 remark 字段和按 remark 模糊查询的接口
- 需要重点关注：新查询接口有没有做输入长度限制和 SQL 注入防护

要求：
- 按严重级别分类输出：阻塞（必须改）、建议（最好改）、可选（风格类）
- 每一条问题必须附带证据：具体 file:line 和一句话说明问题在哪、为什么是问题
- 不要只提风格类意见（命名、格式化）冒充全部结论，重点看：逻辑正确性、边界条件、错误处理、是否匹配需求、是否引入了未声明的行为变化
- 对照这次改动要做的事，指出有没有超出范围的改动
- 找不到问题的地方不要硬凑，如实说"这部分没发现问题"
```

预期报告可能指出：阻塞——`internal/order/service.go:132` 模糊查询直接拼接字符串，未走参数化查询，存在注入风险；建议——迁移文件里 `remark` 列没加长度上限对应的应用层校验；可选——变量命名 `r` 建议改成 `remark`。总体结论给出"存在阻塞问题，需修复后再合并"。
