# 读代码 / 理解模块

适用场景：接手一块不熟悉的代码，需要在动手改之前先搞清楚它是怎么运作的。

## 走哪个通道

都不产出代码改动，所以不占用 Vibe/Spec 产线的通道判断，但产出会作为后续 `/flow-propose` 的输入。

- 只是想看懂、不打算马上改：直接用本手册的提示词模板问 AI，不用建变更。
- 看完发现要改动，且改动超过 Vibe 的三条标准（步数 ≤ 2、单文件、验收一句话说清）：用 `/flow` 走产线，第一步 `/flow-propose` 时把这次分析的结论作为上下文交给 scout，不用重新分析一遍。

## 准备

- 明确要看的模块范围（目录或几个关键文件），范围太大就先缩小，一次只看一个模块。
- 如果是为了后续改动，先想清楚"为什么要看这块"，一并告诉 AI，避免它做泛泛的架构介绍。
- 如果仓库有 `CLAUDE.md` / `AGENTS.md`，确认它是最新的，AI 会先读它。

## 提示词模板

```
帮我梳理 <模块名> 的核心逻辑、依赖关系和数据流，输出一份分析报告，不要改代码。

范围：<目录或文件列表>
目的：<比如"打算给它加一个新字段""怀疑这里有性能问题">

要求：
- 每个结论标出处 file:line，不要凭猜测总结
- 区分"确定如此"和"没读到、推测如此"
- 找不到的东西（比如某个接口的调用方）明确写"未找到"，不要编
- 报告控制在能读完的长度，不要逐文件复述代码
```

## 期望产出

一份分析报告，包含：

- **模块职责**：一段话说清这个模块解决什么问题。
- **核心入口**：路由/handler/命令入口，各带 `file:line`。
- **关键数据流**：请求进来到落库/返回经过哪几层，每层做什么。
- **依赖关系**：依赖了哪些外部服务、其他模块、共享数据结构；被谁依赖。
- **需要注意的地方**：隐含约定、历史包袱、和命名不一致的行为。
- **未解决的疑点**：读代码读不出来、需要人补充的地方。

## 验收

- 抽查报告里 3–5 个 `file:line` 引用，打开源码核对确实是那么回事。
- 报告里"确定"的结论没有和源码矛盾的地方。
- 如果报告的目的是为了后续改动，确认它覆盖了要改的那部分，而不是泛泛而谈整个模块。

## 常见翻车

- **只讲设计模式、不讲这个模块具体干了什么**：提示词模板里明确要求"每个结论标 file:line"，逼它去读具体代码。
- **把没读到的地方脑补成"应该是这样"**：要求区分"确定"和"推测"，未找到的写"未找到"。
- **报告写成逐文件复述源码**：要求控制长度、只写结论不贴大段代码。
- **范围太大导致报告浮于表面**：准备阶段就把范围收窄到一个模块，看不完就分几次看。

## 示例

需求：接手订单模块，打算加一个按备注查询的接口，先搞清楚现状。

```
帮我梳理订单模块的核心逻辑、依赖关系和数据流，输出一份分析报告，不要改代码。

范围：internal/order/
目的：打算给订单加一个 remark 字段和按 remark 查询的接口，需要先搞清楚现有的查询接口和数据模型是怎么组织的

要求：
- 每个结论标出处 file:line，不要凭猜测总结
- 区分"确定如此"和"没读到、推测如此"
- 找不到的东西（比如某个接口的调用方）明确写"未找到"，不要编
- 报告控制在能读完的长度，不要逐文件复述代码
```

预期报告会指出：订单的核心 model 在 `internal/order/model.go:20`，现有查询接口 `ListOrders` 在 `internal/order/service.go:80`（按状态、时间范围查询，未按文本字段查询过），数据库表 `orders` 的字段列表和迁移文件位置，以及"未找到 remark 相关的历史设计，判断为全新需求"。这份报告接下来会作为 `/flow-propose` 的上下文，不用重新分析。
