# 补单元测试

适用场景：给一个已有方法（尤其是分支较多的方法）补齐单元测试，覆盖主干场景。

## 走哪个通道

只给一个已存在的方法补测试、不改被测代码本身：多数情况下只涉及一个测试文件，符合"单文件"；但分支多的方法往往需要拆成多个用例、来回调整，步数容易超过 2。判断标准：

- 补测试不需要改动被测代码，且能一次写完不用来回改：走 **Vibe 通道**。
- 补测试过程中发现被测代码本身需要改（比如为了可测试性要拆函数、加依赖注入），或者测试要覆盖的场景本身有争议：走 **Spec 产线**，先把"要不要改被测代码"这件事讲清楚。

## 准备

- 找到目标方法的源码位置，数一下有几个分支（if/switch/早返回），明确要覆盖哪些。
- 明确测试运行环境的限制：能不能连真实数据库、要不要起容器、外部依赖怎么处理（本仓库的 mock/stub 方式）。
- 找一个本仓库已有的、风格认可的测试文件作参考，让 AI 照着写，而不是自创一套写法。

## 提示词模板

```
给 <文件路径>:<函数名> 生成单元测试，覆盖主干场景。

背景：
- 该函数的分支情况：<简述，或者"你自己先看代码列出分支">
- 测试风格参考：<现有测试文件路径>
- 外部依赖处理方式：<比如"用 xxx 包 mock"，明确说"不启动容器，不连真实数据库">

要求：
- 不修改被测函数本身；如果发现测试不出来是因为代码本身不可测，先停下来告诉我，不要为了能测而顺手改生产代码
- 列出这个函数的所有分支，逐个说明测试是否覆盖了，没覆盖的说明原因
- 所有外部依赖（数据库、网络、时间、随机数）必须 mock 或注入固定值，测试不能依赖真实环境，也不能起容器
- 测试要能重复跑、跑多次结果一致
- 跑一次测试，报告实际输出（通过/失败/覆盖率，如果有工具支持）
```

## 期望产出

- 新增或扩展的测试文件，覆盖目标函数的主干分支。
- 一份分支覆盖清单：函数里有哪些分支，测试用例分别对应哪个，有没有遗漏及原因。
- 外部依赖的处理说明：用了什么方式 mock，为什么这样够用。
- 实际运行结果：跑了多少条用例、是否全部通过。

## 验收

- 本地实际跑一次测试命令，确认通过，且没有连外部服务、没有起容器（观察是否有网络请求或容器启动的迹象）。
- 对照分支覆盖清单，抽查 1-2 个分支，确认测试确实触发了它（可以临时改错代码看测试是否失败）。
- 反复跑两次，确认结果一致，不是偶发通过的 flaky 测试。
- 确认被测代码本身没有被改动（如果改了，是否经过确认、是否合理）。

## 常见翻车

- **测试连了真实数据库或起了容器**：跑起来慢、且在别人机器上可能失败。提示词模板明确要求 mock、不起容器。
- **只测了 happy path，分支多的方法漏了一半**：要求先列出所有分支再逐个对应用例。
- **为了让测试好写，偷偷改了被测函数的签名或逻辑**：要求发现不可测时先停下来问，不要顺手改生产代码。
- **测试里断言写得很松（比如只判断 err == nil），没验证实际行为**：验收阶段抽查断言内容，确认覆盖了返回值/状态变化，不只是"没报错"。
- **依赖当前时间/随机数导致偶发失败**：要求时间、随机数一律注入固定值。

## 示例

需求：给订单状态流转方法补测试，该方法有 5 个分支（新建→已支付→发货→完成，以及取消）。

```
给 internal/order/service.go:TransitionStatus 生成单元测试，覆盖主干场景。

背景：
- 该函数的分支情况：你自己先看代码列出分支
- 测试风格参考：internal/order/service_test.go 里已有的测试
- 外部依赖处理方式：数据库操作用现有的 repo 接口 mock，不启动容器，不连真实数据库

要求：
- 不修改被测函数本身；如果发现测试不出来是因为代码本身不可测，先停下来告诉我，不要为了能测而顺手改生产代码
- 列出这个函数的所有分支，逐个说明测试是否覆盖了，没覆盖的说明原因
- 所有外部依赖（数据库、网络、时间、随机数）必须 mock 或注入固定值，测试不能依赖真实环境，也不能起容器
- 测试要能重复跑、跑多次结果一致
- 跑一次测试，报告实际输出（通过/失败/覆盖率，如果有工具支持）
```

预期产出会列出 5 个分支各对应哪个测试用例（新建→已支付、已支付→发货、发货→完成、非法流转报错、取消场景），repo 接口用现有 mock 包 stub，跑测试报告"5 个用例全部通过"。
